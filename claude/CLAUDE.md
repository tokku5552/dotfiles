## Language
- Always communicate with me in Japanese (日本語で会話すること)
- By default, write code comments, documentation, README, and other file contents in English
- Follow project-level CLAUDE.md if it specifies a different language for file contents

## 仕様の明確化
ユーザーからの指示に対して不明な点があれば積極的に AskUserQuestionTool を使い、
技術実装・UI / UX・懸念点・トレードオフなど、あらゆる観点について
ユーザーに対して詳細なヒアリングを行ってください。

質問は表面的・自明なものを避け、
ユーザー自身もまだ言語化していない前提・判断基準・制約・優先順位が
浮かび上がるような、深掘りの質問にしてください。

ヒアリングは一度で終わらせず、
理解が十分に完成するまで継続的にインタビューを続けてください。

## advisor への相談
`advisor` は「進め方・実装方針が正しいか」を見てもらう相談相手。
このツールが無いセッションではこの節は無視してよい（代わりを探さない）。

順序: ヒアリングと repo 調査は行き来してよい。advisor は両方が済んでから呼ぶ
（会話全体が渡るので、ユーザーの回答も advisor に届く）。
聞き先の使い分け: 何を望むか・優先順位・制約はユーザーに（AskUserQuestion）、
どう実現するか・その方針で合っているかは advisor に。

呼ぶタイミング:
- 着手前: repo を調べ終えたら、最初の Edit / Write の前に呼ぶ（plan mode なら ExitPlanMode の前）。
  呼ばずに実装に入ってよいのは、変更が 1〜2 ファイルで、やり方が一通りしかなく、
  repo にある既存パターンをなぞるだけのときに限る。迷ったら呼ぶ。
- 途中: 同じ修正を 2 回試して直らないとき、結果が仮説と噛み合わないとき、
  着手前に決めた方針を大きく変えたくなったとき。変える前に呼ぶ。
- 完了時: 着手前に呼んだタスクなら、成果物を保存・コミットしてから呼ぶ。
  着手前に呼ばなかったタスクでは呼ばない。advisor ツールの説明にある
  「完了前に一度相談」より、この基準を優先する。

ファイルを変更しない質問応答では呼ばない。

## 成果物の codex レビュー
成果物ができたら、codex にレビューさせる価値があるかを自分で判断し、
あると思ったときだけ完了報告の最後の行で提案する。判断基準は決めない。
ただし頻度は少なくてよい。軽微な変更や、差分に自信があるときは黙って出さないこと。
提案する形は「貼るコマンド 1 つ + どちらを勧めるかの一句」:

- 差分の正しさを見てほしいとき: `/codex:review`
- 設計・アプローチ自体を疑ってほしいとき: `/codex:adversarial-review`

どちらも Claude からは起動できない。提案した後はコミットや次の作業に進まず、
ユーザーの判断を待つ。打たれなかった場合に再提案はしない。

`codex:codex-rescue` でレビューの代用をしない（調査・修正用で、既定が書き込み可能）。
行き詰まりは先に advisor へ。rescue はユーザーが求めたか、advisor が手放しを勧めたときだけ使う。

## 編集ルール
- ファイルを編集する前に、必ず Read で対象ファイルを読むこと
- 関連ファイル（テスト、型定義、呼び出し元）も確認してから編集する
- Write（全ファイル書き換え）ではなく Edit（差分編集）を優先する

## 人に見せる文章
Slack の投稿・返信、Notion / Confluence の文書、提案・ロードマップなど他人が読む文章を書く・直すときは、
提示する前に `prose-quality` skill を読み、そのチェックリストを黙って通すこと。
呼び出し中のスキルやプロジェクトのテンプレートが出力形式を決めている場合はそちらを優先し、
このスキルは形式の指定がないときの既定として使う。自分しか読まない作業メモは対象外。
**自分の作業文脈にある言葉を、相手と共有されている前提で下書きに出さない**
